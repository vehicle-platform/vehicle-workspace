### FW-1 — No on-target verification of watchdog, MPU, stack, WCET
**Current:** grep over rt-core/safety-node `src/`, `tests/`, CMake finds no IWDG/WWDG/MPU/`uxTaskGetStackHighWaterMark`/DWT code at all. Only prose: safety-node CLAUDE.md:27 (own IWDG), rt-core `src/features/cornering/README.md:128` (WCET budget lean_ekf_step <= 1 ms "measured on the board with DWT CYCCNT, Q-019"), :103 (task priorities "checked on HIL"). HALs are host-only (`rt-core/src/hal/host/`, `safety-node/src/hal/host/`); target presets cross-compile only `vehicle_rtcore_logic`. Table row is correct; T13 is rt-core only, **safety-node has no equivalent card** (T12 is IMU only).
**Target:** a `target-verify` layer on both MCUs: (a) IWDG (+WWDG window on G474) fed only by a supervisor that checks per-task alive bits; (b) static MPU map; (c) stack painting + high-water-mark log; (d) DWT WCET probes with budgets asserted; (e) Renode smoke for H743 in CI, real board for G474.
**Steps:**
1. Host first (no hardware): add `src/services/task_alive` (bitmask, deadline per task, pure C, Unity tests) and `wcet_probe.h` (macro, DWT->CYCCNT, `DWT->LAR`/`DEMCR.TRCENA` init; host stub uses clock_gettime). Budgets in one table: lean_ekf_step 1 ms, comms_pass, uds_client_step.
2. rt-core H743 (T13): `configCHECK_FOR_STACK_OVERFLOW=2`, `configUSE_TRACE_FACILITY=1`; log `uxTaskGetStackHighWaterMark` per task into the 0xFD02 health DID; IWDG started from option byte `IWDG1_SW=0` (hardware watchdog, red-zone option-byte init) or at boot before the scheduler; freeze in debug via `DBGMCU->APB4FZ1`. MPU (Cortex-M7, 16 regions): flash RO+X, SRAM data XN, null-page no-access, one stack-guard region per task (or main stack), and **FDCAN message RAM / DMA buffers as non-cacheable** (D-cache coherency is the classic M7 bug).
3. Renode: `platforms/cpus/stm32h743.repl` exists upstream; run the ELF headless with a `.robot` test (boot, FreeRTOS tick, UART marker, IWDG reset on a stuck task via a test hook). **STM32G474 has no stock Renode platform I could find** (verify in `platforms/cpus/`); for safety-node use the NUCLEO-G474RE + hil-bench, not Renode, or write a minimal repl (M). Renode does not prove timing: WCET only on silicon.
4. safety-node G474 (bare metal): IWDG with window (`IWDG->WINR`) fed once per main-loop iteration only after all safety checks passed; main-loop deadline measured by DWT; MPU (8 regions on M4F) minimal: null guard, flash RO, stack guard; stack painting (0xDEADBEEF fill, scan at 1 Hz, fault if < 25 % free).
5. WCET method: DWT CYCCNT over >= 1e6 iterations under worst-case input (fault injection, full RX FIFO, ISR load), record max + p99.99, fail CI/HIL job if max > budget x 0.8 margin. ISO 26262-6 also expects resource-usage evidence (stack, timing) for the software unit/integration level; keep the numbers in `docs/` evidence files per release.
6. HIL (vehicle-hil-bench, STM32F4 restbus): scenarios "stuck task -> IWDG reset <= X ms", "rt-core silent -> safety fallback (D-042)".
**Acceptance:** each MCU resets within the configured IWDG timeout when the supervisor is starved (measured, logged); all tasks >= 25 % stack free after 1 h soak with fault injection; max WCET of every budgeted function <= 80 % of budget over 1e6 runs; MPU fault handler test (write to null page, execute from SRAM) traps and logs; Renode job green in rt-core CI; safety-reviewer pass on each PR (invariant 8: watchdog, MPU, linker, option bytes).
**Effort:** L · **Depends on:** NUCLEO-H743ZI2 + NUCLEO-G474RE on the desk, T6 (pin plans/CubeMX .ioc), user for option-byte programming (WDG_SW, RDP stays 0 on prototype; RDP level 2 is irreversible, do NOT set) · **Card:** T13 (rt-core) + **new card T25 "safety-node on the G474: IWDG/MPU/stack/WCET"**

## R4 — architecture and CI (research 2026-11-17)

### ARCH-1 - Monorepo vs multirepo + automation
**Current:** 13 repos, 7-8 pin defs via submodule to a tag; one defs change = defs PR + tag + release + ~8 repin PRs (T1 is that backlog, T2/T3 are the stalled consequences). Shared text (PLATFORM-RULES, agents) is copied into every repo by `scripts/sync_claude.py` (rule change = 11 PRs). Per-repo CI exists, no cross-repo CI: a defs change is not tested against consumers before release.
**Target (recommendation: do NOT do the full monorepo now; do "multirepo + automation" first, and a scoped mini-monorepo only if pain persists):**
Phase A (S/M): Renovate (or a scripted `repin` workflow) opens the repin PRs; a defs-side "consumer smoke" workflow checks out consumers at main with the defs PR commit; reusable workflows + shared Claude assets by sync (exists). Phase B (optional, L): merge only the tightly coupled, same-lifecycle set (defs + rt-core + safety-node + server + linux-node + ml) via filter-repo; keep analyzer, mobile, mcp, conn separate.
Comparison table:

| Criterion | Full monorepo (proposed) | Multirepo + automation |
|---|---|---|
| Cross-cutting change | 1 PR, atomic CI | defs PR + auto repin PRs (Renovate), 1 human click each, or agent-merged |
| Defs tag/release ceremony | Gone inside monorepo; still needed for analyzer/mobile mirror | Stays, but automated (release-please + Renovate) |
| CI complexity | High: path filters + aggregate check, mixed toolchains (PlatformIO, CMake, uv, npm, cargo, flutter) in one repo, caches | Low per repo, already working |
| Migration cost | L: filter-repo x8, tag renames, rewrite CI, `.claude` sync, CLAUDE.md, manifest, DECISIONS refs, VS Code workspace, setup.sh | S/M |
| Issue/PR links | Issues cannot be transferred with history across a merged repo; old PR numbers dangle (links in DECISIONS/ISSUES/STATUS point at `repo#NN`); archived repos keep them readable | Preserved |
| History/SHAs | Rewritten SHAs (every `commit abc1234` mention in docs/manifest breaks); tags need prefix (`rt-core/v0.8.0`) | Untouched |
| Mirror for defs (subtree split) | Extra moving part: force-push-ish split, non-deterministic SHAs, loops, needs PAT/deploy key, tag mirroring by hand; breaks submodule pins when split SHAs change | None |
| Public-repo optics (thesis) | One repo, good for reviewers | 13 repos, harder to browse (README index mitigates) |
| Reversibility | Low (one-way door) | High |
| Fits "one dev + AI" | Yes in principle, but agents already work in per-repo worktrees; monorepo makes every session load/CI everything | Yes |
Honest verdict: the pain is the repin fan-out and shared-text duplication, both solvable by automation at S/M cost; monorepo buys atomicity but costs L effort, SHA/link breakage and a fragile subtree mirror right before hardware work resumes.
**Steps:** 1. Decide (user): multirepo+automation now, revisit at a stated trigger (e.g. >3 repin waves per month after Phase A, or commercial multi-vehicle phase). 2. Add `renovate.json` with the git-submodules manager (set `branch = vX.Y.Z` in `.gitmodules`? see CI-3; fallback: a `repin-defs.yml` workflow triggered by `repository_dispatch` from defs release that opens repin PRs in all consumers with `gh`). 3. Add defs-side `consumers.yml` (matrix over server, linux, ml, rt-core host tests, analyzer) that checks out each consumer main and points its submodule at the PR SHA; informational first. 4. Move repin PR bodies to a template listing tests. 5. Only if Phase B chosen: dry-run in scratchpad: `git clone --mirror`, `git filter-repo --to-subdirectory-filter firmware/rt-core --tag-rename '':'rt-core/'`, merge with `--allow-unrelated-histories`; use `git replace`-free; keep old repos archived (not deleted) so PR/issue links stay readable; rewrite `repo#NN` references to full URLs first. 6. Defs mirror (if ever): `git subtree split --prefix=defs -b mirror` in CI pushed with a deploy key to a mirror repo; pitfalls: split SHAs stable only if the split is always done from full history (never shallow, `fetch-depth: 0`), commits touching both prefix and outside get synthetic variants, tags must be re-created on split SHAs (`git subtree split` does not carry tags), concurrent runs race, submodule pins to mirror tags must be created by the same job; use `splitsh-lite` for speed. Alternative with fewer pitfalls: publish defs releases as a tarball/wheel (versioned artifact) and let analyzer/mobile download it instead of a submodule.
**Acceptance:** Phase A: a defs release opens N repin PRs automatically (verified on one release); a defs PR shows a consumer-matrix result; manual repin time per release < 10 min. T1-style backlogs do not recur.
**Effort:** Phase A S/M; Phase B L · **Depends on:** CI-3, CI-4 · **Card:** new T25 (Phase A "cross-repo automation"); Phase B deferred card, user decision
**Sources:** [git filter-repo manual](https://man.archlinux.org/man/git-filter-repo.1.en), [Netlify multirepo to monorepo](https://developers.netlify.com/guides/migrating-git-from-multirepo-to-monorepo-without-losing-history/), [mono-repo history guide](https://ddingpy.github.io/mynote/posts/mono-repo-git-history-migration-guide/), [Renovate git-submodules](https://docs.renovatebot.com/modules/manager/git-submodules), [GitHub: troubleshooting required checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks), [splitsh-lite](https://github.com/splitsh/lite)

`.mailmap`: rewrites NOTHING in the stored commits. If the user ever changes mind: only `git filter-repo --mailmap` plus force-push on all repos, then GitHub Support request to purge cached views and run "sensitive data removal"; rotate nothing (it is not a secret) but SHAs change: do it before any monorepo migration if at all, since ARCH-1 Phase B already rewrites history once (combine, single disruption).
